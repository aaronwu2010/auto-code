```

│                    AI 助手智能架构                              │
├──────────────────────────────────────────────────────────────┤
│                                                              │

│  ┌─────────────┐  ┌──────────────┐  ┌─────────────────────┐  │

│  │ "停下来想想"  │  │ "这次学到了啥" │                            │
│  └─────────────┘  └──────────────┘                            │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### ❌ 缺失（4 个高级智能模式）

|---|------|-----------|-----------|

| **B** | 执行中主动搜索 | 工具返回空结果 / 置信度低时，自动追加 Grep/Read | 不等 LLM 显式请求，agent 自己判断"我还需要更多信息" |
| **C** | 多方案量化比较 | "方案 A 改动 5 个文件，性能 +20%；方案 B 只改 1 个文件，但性能 -10%" | 不只会给一个答案，会说清 trade-off |
| **D** | 注意力聚焦 | 长任务中高亮"当前 Top 3 焦点"，抑制次要信息 | 上下文再长也能抓重点，避免"看了一堆但没抓住关键" |

## 三、实施计划（补齐 4 个高级模式）

### 阶段 A：假设驱动探索器 `HypothesisExplorer`

**核心思想：** 不盲目扫描整个项目，先提出几个合理假设，再有针对性地搜索验证。

**工作流程：**
```
用户: "为什么登录会超时？"

HypothesisExplorer 自动生成假设:
  H1: 网络连接问题 → 搜索 timeout / connection refused
  H2: 数据库连接池耗尽 → 搜索 pool / max connections
  H3: 认证服务死锁 → 搜索 auth / lock / mutex

然后并行验证每个假设（Grep），返回最可能的根因。
```

**文件：** `internal/engine/query/hypothesis_explorer.go` (~300 行)
**集成点：** Landscaper 之后、CallModel 之前，当任务是 debug/分析类时自动触发

---

### 阶段 B：主动搜索触发器 `ProactiveProbe`

**核心思想：** 当 agent 发现"信息不足"时，不等 LLM 指令，自己追加搜索。

**触发条件：**
- Grep 返回 0 结果（可能关键词不对）→ 自动换同义词再搜
- Read 得到很短的内容（可能文件不对）→ 自动搜索相关文件
- 置信度 < 0.4（UncertaintyEngine 判定）→ 自动追加 1-2 个探测工具调用

**文件：** `internal/engine/query/proactive_probe.go` (~250 行)
**集成点：** UncertaintyEngine 后置 hook + Grep/Read 工具结果处理后

---

### 阶段 C：多方案比较器 `AlternativeAnalyzer`

**核心思想：** 不只给一个答案，同时提出多个方案并量化比较。

**输出格式：**
```
我建议 3 种方案：

方案 A：最小改动（改 1 个文件，3 行代码）
  优点：风险低、易回滚
  缺点：性能影响小 (-5%)
  置信度：85%
  
方案 B：均衡方案（改 2 个文件，20 行代码）
  优点：性能 +15%，代码更清晰
  缺点：需要改公共接口
  置信度：75%  ← 推荐
  
方案 C：彻底重构（改 5 个文件，150 行代码）
  优点：长期最优，性能 +40%
  缺点：风险高，需要完整回归测试
  置信度：60%
```

**文件：** `internal/engine/query/alternative_analyzer.go` (~280 行)
**集成点：** 最终回答生成前，自动评估是否需要多方案比较

---

### 阶段 D：注意力聚焦管理器 `FocusManager`

**核心思想：** 长任务中动态管理"当前焦点"，抑制次要信息。

**工作机制：**
- 每轮迭代更新 Top 3 焦点（基于 GoalTracker 状态 + 最近失败/成功）
- 注入到 messages 开头，让 LLM "眼睛里有活"
- 自动衰减旧焦点（3 轮没推进就降级）

**文件：** `internal/engine/query/focus_manager.go` (~200 行)
**集成点：** CallModel 前（最早注入，让 LLM 第一眼看到）

**实施顺序：A → B → D → C**

## 六、设计原则

1. **全部可降级：** 每个新模块都有 nil 降级路径，零副作用
2. **零 LLM 开销优先：** 能用规则/启发式解决的就不调 LLM
3. **失败即跳过：** 所有外部命令失败时静默跳过，不中断主流程
4. **动态上下文：** 新模块的输出通过 meta message 注入，不污染正常对话
5. **经验自动持久化：** 关键发现自动写入 ExperienceStore
